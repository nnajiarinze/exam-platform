# Svea Study mobile authentication

## Architecture audit

The mobile app uses Expo AuthSession and Expo WebBrowser. On iOS this opens an
`ASWebAuthenticationSession`; Android uses the platform browser/Custom Tabs.
No WebView or native password form is used. The flow is OIDC Authorization Code
with PKCE (`S256`), an opaque state generated and checked by AuthSession, and a
per-attempt nonce checked against the returned ID token.

The callback is `sveastudy://auth/callback`. It is registered as an iOS URL type,
an Android intent filter through the Expo scheme, and an exact redirect on the
Keycloak `mobile-app` public client. The app exchanges a code once, using the
request's in-memory verifier. Access-token issuer, audience, subject and expiry
are checked before use. ID-token issuer, client audience, nonce, subject and
expiry are checked on interactive login. Learning and Content APIs remain the
cryptographic enforcement points through Spring Security and Keycloak JWKS.

Refresh tokens and the minimal resumable session are stored in Expo SecureStore
(iOS Keychain / Android encrypted Keystore-backed storage), namespaced by LOCAL
or HOSTED. Tokens are not written to AsyncStorage, URLs or ordinary logs. An
unexpired access token may restore an offline UI session; protected API calls
still require backend validation when connectivity returns.

LOCAL uses the local Keycloak issuer and permits email login/registration.
HOSTED is pinned to
`https://api.tinkona.com/auth/realms/exam-platform`. Production builds
reject LOCAL or cleartext configuration.

## Native experience

The unauthenticated entry screen presents Svea Study in Swedish with explicit
Apple, Google, email and registration actions. Provider buttons are enabled only
when the corresponding broker is configured for that build. A system
authentication sheet is explained before launch. Loading has fixed-size button
content, concurrent sessions are locked, cancellation is quiet, and safe
diagnostic codes map to user-facing copy without exposing OAuth payloads.

## Keycloak policy

The versioned `svea-study` login theme is packaged in the immutable Keycloak
image and applied by realm hardening. Registration, email verification, password
reset, unique email, brute-force protection and PKCE remain required. Swedish is
the realm default and English remains an explicitly supported locale.

Google is configured only when both protected `KEYCLOAK_GOOGLE_CLIENT_ID` and
`KEYCLOAK_GOOGLE_CLIENT_SECRET` exist. It is hidden from generic/Admin login and
selected by the mobile `kc_idp_hint`. `trustEmail` is disabled, tokens are not
stored, and Keycloak's first-broker-login flow requires explicit confirmation
and re-authentication before linking an existing account. There is no automatic
merge based on an unverified email.

## External and backend gaps

- No Apple or Google provider credentials are currently present in the checked
  LOCAL/HOSTED configuration. The native controls therefore remain disabled and
  cannot be physically completed yet.
- Keycloak 26.7 does not ship an Apple social provider. Apple differs from plain
  OIDC (signed client-secret rotation, POST callback, first-login name/email), so
  a compatible reviewed provider extension and Apple Services ID, Team ID, Key
  ID and protected `.p8` material are required. No third-party extension or
  private key is silently introduced by this change.
- Linked-method listing, safeguarded unlink, sign-out-all, identity deletion and
  append-only identity-link audit require a privileged identity-management BFF.
  The mobile app must not receive Keycloak administration credentials. Existing
  learner anonymisation remains separate; full identity deletion is not claimed.
- Privacy, terms and help links remain visibly handled but report unavailable
  until publication URLs are configured.

Learner identity remains keyed by the stable Keycloak subject. No learning rows,
progress, Practice history, Mock Exam history, authoring data or content release
are migrated or regenerated by this work.
